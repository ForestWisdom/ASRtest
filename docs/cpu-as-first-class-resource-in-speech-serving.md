# 将 CPU 视为语音模型 Serving 的一等资源

> 原文：[重新审视 CPU 资源作为语音模型 Serving 过程的一等公民](https://zhuanlan.zhihu.com/p/2073676263076767071)
>
> 作者：likaige；发布日期：2026-08-20
>
> 本文包含原文总结和面向 ASRtest 的分析。实验数据与框架进展来自原文；项目建议不代表 ASRtest 当前已实现相关机制。

## 核心结论

ASR/TTS serving 通常由大量短请求和高并发组成。GPU kernel 可能只运行几微秒，CPU 却要持续完成请求构建、stage 调度和 kernel launch。因此，系统即使 GPU 利用率很低，也可能已经受到 host orchestration 限制。优化这类系统不能只关注 GPU，还应把 CPU 时间、物理核拓扑、同机争用和编译缓存纳入资源预算。

## 从 CI 回退定位到 CPU

SGLang Omni 使用严格的性能 CI：每次性能提升后重复 5 次，取最低值作为新门槛。一次校准把 Fun-ASR 门槛从 115.3 req/s 提高到 128.2 req/s，五次结果在 128～139 req/s；随后相同代码、依赖、GPU 和压测脚本的测试最低只有 36 req/s，跨轮差距接近 4 倍。

控制变量实验表明，同机 CPU 负载越高，ASR 吞吐越低；重负载时约为 27 req/s，GPU 利用率也降至个位数。校准恰好发生在 CI 空闲时段，而失败集中在每小时任务数明显增加后。这说明回退并非模型或 GPU 算子本身变慢，而是未被调度系统管理的 CPU 资源发生波动。

FlashInfer JIT 缓存失效进一步放大了问题：镜像预热未覆盖 cutlass MOE，预热使用 Python 3.12 而 CI 使用 Python 3.11，现场编译产物又随容器销毁。缓存未命中会触发长时间编译，并把同机 ASR 服务从 122 qps 压到 41 qps。补全预热产物并统一 Python、Torch 与 FlashInfer 后，`fused_moe` 首次调用由 481 秒编译缩短为 1.4 秒加载。

## 为什么语音 Serving 容易受 CPU 限制

语音请求进入 SGLang Omni 后，host 侧需要拆解请求、在多个 stage 间调度，并反复向 GPU 派发短小任务。相较长上下文 LLM 的长 prefill 和长 decoding，语音 workload 的固定 host 成本占比更高。原文引用的早期 H100 profiling 中，GPU 有 94.3% 的时间在等待；host CPU 配额降至约四分之一会让吞吐下降约七成，而 GPU SM 频率降至 0.455 倍只使吞吐下降约一成。作者同时注明，后续 runtime fusion 已明显改善这一早期结果。

CPU 资源不只是“核数”。Higgs TTS 实验中，把可用核从 32 个降到 2 个几乎不影响吞吐；把 cgroup CPU quota 降到 25% 后，吞吐却只剩 16%。这表明近似串行的 host 链更依赖及时、稳定的 CPU 执行时间，简单增加可见核数未必有效。

### 争用不等于排队

同机进程可能落到相同物理核或一对 SMT sibling 上，共同争夺执行单元、缓存和功耗预算。原文用 PSI 和“每请求 CPU 毫秒数”区分排队与争用：排队应使 PSI 升高；同核争用则可能让 PSI 仍很低，但每毫秒完成的工作减少。

Fun-ASR 共享核实验中，PSI 始终低于 0.01，但每请求 CPU 时间从 51～52 ms 增至 72～83 ms，吞吐从约 82 req/s 降至 48～58 req/s。独占完整物理核及其 SMT sibling 可保留约 92% 的安静基线吞吐；不隔离时只剩 55%～62%。因此 cgroup quota 只能控制总量，cpuset 才能防止进程挤在同一物理核上。

## 治理方式与效果边界

CI 修复包括：为每条 GPU lane 预留 cpuset；检测核区内的外来 CPU 占用并重跑受污染样本；把单测、环境准备和 runner 进程树纳入相同核区；将开发任务迁走，使整机专用于 CI。调度任务时由此可以同时检查 CPU 和 GPU 预算。

作者进一步设计了感知物理拓扑、覆盖整棵进程树的 CPU allocator。它的价值是自动生成全机一致的放置方案和暴露争用，而不是比人工调好的 CPU mask 更快。在外部重负载下，allocator 使 Fun-ASR、Qwen3-ASR 吞吐分别达到未隔离时的 3.54×、2.50×，并各自保留 98% 的空载吞吐。

但在没有外部 CPU 负载的单机 DP + MPS 生产实验中，18 个配对点平均只变化 +0.43%，各档位在 -3.68%～+5.34% 之间，没有稳定收益。独占部署的 CPU 核充足时，操作系统调度通常已经够用，静态划分不当还可能降低性能。因此文章的结论不是“所有语音服务都应该绑核”，而是：CPU 隔离主要用于保护服务免受外部任务干扰，应由真实争用证据驱动。

## 对 ASRtest 的建议

以下建议结合本项目在 8× RTX 5090 服务器上使用 SGLang-Omni、以单卡运行 Qwen3-ASR-1.7B 的约定提出。

1. **联合观察 CPU、GPU 与吞吐。** 验收除 HTTP 成功和转写正确外，还应记录请求延迟或吞吐、GPU 利用率、CPU 利用率及同机任务。GPU 利用率低时，应先排查 host 调度和 CPU 争用。
2. **隔离服务与重型编译。** 不要在承载 ASR 的 CPU 核区同时执行 FlashInfer/Torch JIT、环境重建或大规模测试。`nvidia-smi` 和端口检查之外，还需关注 CPU 工作负载。
3. **保持环境与缓存一致。** 复用 `/home/sdu/zhangzhisen/sglang-omni/.venv`，避免每次启动创建不同 Python 版本的环境。升级 Python、Torch、FlashInfer 或 SGLang-Omni 后，应预期 JIT 缓存失效，并在非服务窗口完成首次编译。
4. **先诊断，再绑核。** 若相同模型、音频和并发设置出现吞吐漂移，应对比安静/繁忙时段，检查每请求 CPU 时间、PSI、CPU affinity 和 SMT 拓扑；确认外部争用后，再评估 cpuset/cgroup。
5. **用真正的并行利用多核。** 单条 host 链无法通过增加可见核数线性加速。需要提升吞吐时，可在显存和稳定性允许的前提下基准测试多进程、多副本或 DP + MPS，但不应未经验证改变当前单卡默认配置。
6. **固定性能测试条件。** 未来若加入吞吐门槛，应固定模型与依赖版本、并发、测试音频、CPU 放置和同机负载，并重复测试取保守值，避免把机器状态变化误判为代码回退。

## 总结

短请求、高并发的语音 serving 中，CPU 承担的请求构建和跨 stage 调度可能成为决定吞吐的串行路径；外部进程还会通过物理核、SMT、缓存和功耗争用增加每请求 CPU 成本。合理顺序是先用可复现基准确认瓶颈，再处理环境与 JIT 缓存一致性、外部任务隔离、host 路径优化和多进程并行。CPU allocator 是高争用环境的保护工具，而不是所有生产部署都应默认开启的性能开关。
